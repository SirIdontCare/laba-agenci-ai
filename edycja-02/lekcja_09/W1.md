# L09 · W1 — Ten sam silnik bez otwartego czatu

**CORE: 15 min. Efekt:** ręcznie uruchamiany, serwerowy briefing. Wymagane: runs i misje z L08.

## Zbuduj

1. Wydziel funkcję wykonawcy zadania z UI: `runMission({ownerId,missionId,input,runKey})`. ownerId pochodzi z uwierzytelnionego kontekstu lub zapisanej konfiguracji zadania, nigdy wyłącznie z dowolnego body.
2. Ręczny przycisk wywołuje chroniony endpoint. Zadanie zapisuje queued/running oraz wynik succeeded/partial/failed. Nie stosuj fire-and-forget po odpowiedzi HTTP w środowisku serverless.
3. CORE jest krótkim zadaniem mieszczącym się w limicie hostingu. Gdy misja wymaga dłuższej pracy, użyj trwałej kolejki/wykonawcy; samo zwrócenie 202 nie oznacza, że proces będzie działał dalej.
4. Przygotuj briefing ze źródłami, czasem danych i stanem braku. Wszystkie runy mają ownera i osobny koszt. Błąd nie tworzy pustego rekordu „sukces”.
5. Zapisz runKey dla ręcznej próby. Powtórne żądanie z tym samym kluczem zwraca istniejący stan lub konflikt, nie drugie wykonanie.

## Polecenie do asystenta

```text
Wydziel istniejącą misję do serwerowego wykonawcy z runKey i trwałym stanem. Dodaj manual trigger z autoryzacją. Bez pracy w tle po zakończeniu requestu, chyba że używasz rzeczywistej trwałej kolejki. Testuj sukces, błąd, timeout i ponowne żądanie tej samej misji.
```

## Odbiór

Po zamknięciu UI zapisany rezultat pozostaje w bazie; autor ma dostęp, inny user nie; timeout jest widoczny; ponowne identyczne żądanie nie nalicza kolejnego runa.

**Ratunek:** jeden odczyt i jeden model call w ramach czasu requestu. **STRETCH:** job queue, lease i odzyskiwanie po przerwaniu workera z testem, nie tylko diagramem.
