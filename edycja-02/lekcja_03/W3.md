# L03 · W3 — Model wybiera narzędzie, program pilnuje kontraktu

**CORE: 20 min. Efekt:** jeden agent z czytelną osią wywołań. Wymagane: W1/W2, kontrakt L02.

## Zbuduj

1. Dodaj `getOffer(plan)` dla start/team z `data/fixtures.json`. Zwraca kwotę netto, liczbę kont, source_id i wersję; nie czyta dowolnych ścieżek czy SQL.
2. Dodaj `calculateTotal(monthlyNet,months)`: liczba nieujemna i całkowite months 1–24. Wynik arytmetyczny nie jest ofertą roczną ani rabatem. Nie używaj eval ani new Function.
3. Zarejestruj tools z typowanym inputem, precyzyjnym opisem i backendową walidacją. Wynik narzędzia wraca do modelu z odpowiednim tool_call_id [OR-TOOLS]. Stan UI opieraj na rzeczywistych zdarzeniach, nie opisie „wykonałem”.
4. Narzędzia internetowe i obrazowe pozostają oddzielnie rozliczane i uruchamiane tylko dla uprawnionego żądania. Łączenie tools i konkretnego pluginu wymaga próby na wybranym modelu; brak zgodności → jawna osobna ścieżka, nie zgadywanie API.
5. Testuj sześć poleceń: Start; Zespół; arytmetyczna suma za 3 miesiące; Enterprise; zwykłe powitanie; polecenie „wyślij ofertę”. Ostatnie nie ma narzędzia wysyłającego.

## Polecenie do asystenta

```text
Połącz dozwolone narzędzia na /api/agent. Dodaj getOffer i calculateTotal z walidacją. UI pokazuje nazwę, bezpieczne argumenty, status i wynik faktycznego wywołania. Model nie dostaje narzędzia wysyłki. Nieznane narzędzie i złe argumenty odrzuć. Ogranicz cały przebieg według wspólnego kontraktu.
```

## Odbiór

Start zwraca 490; Zespół 990; 3×490 daje 1470 jako obliczenie, nie zniżkowy abonament; Enterprise → missing_data; powitanie nie uruchamia tools; mail nie został wysłany. Dwa własne narzędzia mają osobne testy.

**Ratunek:** uruchom tools bez modelu, potem dodaj wybór narzędzia. **STRETCH:** rejestr możliwości modelu i automatyczny test kontraktu po jego zmianie.
