# L02 · W2 — Wynik, który aplikacja potrafi bezpiecznie odczytać

**CORE: 20 min. Efekt:** walidowana karta triage. Wymagane: W1 oraz model wspierający structured output.

## Zbuduj

1. Przeczytaj `schemas/triage.schema.json`. Pola: message_id, category, priority, draft, needs_review, missing_data, sources. Nie dodawaj swobodnego SQL, polecenia do shell ani user_id wybieranego przez model.
2. Wywołaj OpenRouter z JSON Schema i `provider.require_parameters=true`. Provider nie może po cichu zignorować wymaganego formatu [OR-JSON]. Obsłuż odmowę modelu, ucięty wynik, błąd parsowania i brak wspierającego providera.
3. Po odebraniu wyniku wykonaj lokalną walidację schematu. Następnie osobne reguły: source_id musi istnieć w przekazanych źródłach; brak ceny Enterprise → nie wymyślaj ceny; missing_data → needs_review=true.
4. Widok pokazuje kategorię, szkic i pola wymagające kontroli. Zły wynik ma status „Do poprawy”, nie zielony sukces. Nie zapisuj niesprawdzonego wyniku do docelowego systemu.
5. W testach jednostkowych zasymuluj prawidłowy JSON, brak pola, zły enum, dodatkowe pole i poprawny strukturalnie, lecz fałszywy source_id.

## Polecenie do asystenta

```text
Dodaj endpoint /api/triage i UI wyniku według schemas/triage.schema.json. Adapter OpenRouter ma używać dostępnego modelu z JSON Schema. Waliduj format i wskazane reguły biznesowe. Rozdziel błąd struktury, brak dowodu i awarię API. Szkic pozostaje niewysłany. Pokaż testy negatywne, nie tylko poprawny przykład.
```

## Odbiór

Każdy z pięciu testów ma rzeczywisty rezultat; fałszywy source_id zostaje odrzucony; model nie wspierający formatu daje jawny błąd; nie ma automatycznej wysyłki. Poprawny JSON nie dowodzi prawdziwości odpowiedzi.

**Ratunek:** sprawdź najpierw schema na ręcznych fixture bez modelu; dopiero potem połączenie live. **STRETCH:** ograniczona, pojedyncza próba naprawy wyniku z ponowną pełną walidacją i osobno policzonym kosztem.
