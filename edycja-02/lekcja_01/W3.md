# L01 · W3 — Link działa także bez Twojego edytora

**CORE: 20 min. Efekt:** wdrożony fundament z barierą dostępu. Wymagane: działające W2 i niski limit klucza zatwierdzony przez Laba.

## Zrób

1. W katalogu aplikacji uruchom testy i build. Sprawdź `.gitignore`, diff i pliki stagingu. `.env.local` nie może trafić do Git. Załóż własne repo projektu; prywatne repo jest prawidłowym wyborem, nie wymuszamy publicznego kodu.
2. Importuj projekt do Vercel. Przed deployem ustaw serwerowe zmienne środowiskowe; nie wklejaj klucza w opis projektu ani w komendę widoczną na nagraniu. Hosting i plan muszą pasować do zastosowania [HOST].
3. Zachowaj demonstracyjną barierę z W2 dla KAŻDEGO płatnego endpointu. Nowa sesja bez dostępu nie może korzystać z API. Sam ukryty przycisk nie jest zabezpieczeniem.
4. Otwórz URL na drugim urządzeniu. Przetestuj jedno pytanie, błędny dostęp i awarię modelu. Nie udostępniaj linku szeroko przed sprawdzeniem bariery i budżetu.
5. Zapisz commit, URL i `artifacts/L01.md`: test lokalny, test wdrożenia, model, znane ograniczenia, czy limit klucza faktycznie ustawiono.

## Polecenie do asystenta

```text
Sprawdź build, testy i brak sekretów w plikach do commita. Przygotuj instrukcję deployu tej aplikacji na Vercel. Nie publikuj bez działającej serwerowej bariery dla płatnych operacji. Po wdrożeniu sprawdź nowy URL bez starej sesji. Wyniki nieuruchomione oznacz NOT RUN.
```

## Odbiór

URL działa przy zamkniętym lokalnym serwerze; błędny dostęp jest odrzucony przed kosztem; klucz nie występuje w JS/HTML/logach; test awarii kończy się kontrolowanie. Sekret opublikowany omyłkowo wymaga unieważnienia, a nie tylko usunięcia pliku.

**Ratunek:** nieudany deploy nie uzasadnia wyłączenia auth. Pozostań lokalnie i zapisz błąd. **STRETCH:** bezpieczny mechanizm ograniczania prób dostępu w trwałym magazynie.

Nadaj aplikacji nazwę i instrukcję konkretnego procesu. Oddaj URL, zrzut wyniku oraz jeden test błędu. Nie oddawaj klucza. Zachowaj działający commit jako własny checkpoint L01.
