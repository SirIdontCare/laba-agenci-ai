# L05 · W1 — Baza z ochroną od pierwszego rekordu

**CORE: 15 min. Efekt:** tabele z właścicielem i RLS. Wymagane: konto Supabase i działająca aplikacja.

## Zbuduj

1. Utwórz projekt Supabase. Używaj wyłącznie fikcyjnych danych. URL i publishable/anon key konfiguruj zgodnie z projektem; klucz secret/service-role nigdy nie trafia do NEXT_PUBLIC_.
2. Dodaj minimalną sesję testowego operatora przez Supabase Auth. To celowo małe przygotowanie do pełnej L07. Nie publikuj bazy z RLS wyłączonym do czasu „lekcji o bezpieczeństwie”.
3. Przeczytaj `reference/schema.sql`: wzorzec conversations i messages z owner_id, kluczem obcym, RLS oraz wymuszeniem zgodnego właściciela rozmowy. Asystent dopasowuje migrację do faktycznego projektu, nie uruchamia kasowania istniejących tabel.
4. Włącz RLS przed udostępnieniem tabel przez API. Odczyt/zapis tylko dla auth.uid()=owner_id. Testowy klient używa sesji, nie administracyjnego klucza, który omija RLS.
5. Sprawdź: anonim nie odczytuje; operator zapisuje własną rozmowę; podstawienie innego owner_id jest odrzucane. Uprawnienia testuj z API, nie tylko w Table Editor zalogowanym jako administrator.

## Polecenie do asystenta

```text
Dodaj minimalny Supabase Auth i bezpieczne tabele conversations/messages, korzystając ze wzorca reference/schema.sql. RLS od początku, owner_id z sesji, pełne polityki odczytu i modyfikacji. Nie używaj service-role do zwykłych zapytań użytkownika. Pokaż migrację przed wykonaniem i test pozytywny oraz negatywny.
```

## Odbiór

Własny zapis działa; anonim nie widzi danych; fałszywy owner_id nie przechodzi. Wiersz messages nie może wskazywać rozmowy innego właściciela. Puste tabele nie są dowodem poprawnego RLS.
