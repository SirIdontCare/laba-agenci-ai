# L07 · W2 — Sprawdź izolację poza interfejsem

**CORE: 20 min. Efekt:** macierz testów A/B/anon. Wymagane: W1, tabele L05/L06.

## Zrób

1. Jako A utwórz rozmowę i dokument z fikcyjnym znacznikiem `A_ONLY_TEST_490`. Jako B utwórz `B_ONLY_TEST_990`. Nie są to prawdziwe sekrety; służą wykryciu nieuprawnionego ujawnienia.
2. Testuj SELECT, INSERT z podszytym owner_id, UPDATE i DELETE dla obu kont oraz anon. Cudze dane są niewidoczne albo operacja jest jawnie odrzucona; sprawdź liczbę zmienionych wierszy, nie tylko kod HTTP.
3. Powtórz test przez bezpośredni endpoint aplikacji i RPC wyszukiwarki. W podanym conversation_id lub document_id zastąp ID własne cudzym. Wynik nie może zawierać obcego rekordu.
4. Włącz tymczasowy bezpieczny log identyfikatorów źródeł przed wywołaniem modelu. Udowodnij, że źródło B nie weszło do promptu A. Odmowa wygenerowana PO odczycie cudzych danych nie jest poprawną izolacją.
5. Sprawdź, że relacja messages→conversations nie pozwala podczepić własnej wiadomości do cudzej rozmowy. Warunki egzekwuje DB i backend.

## Polecenie do asystenta

```text
Zbuduj macierz autoryzacji A/B/anon dla danych, endpointów i RPC. Użyj dwóch kont testowych z normalnymi sesjami, nie service-role. Dla odczytu sprawdzaj zawartość, dla zapisu także liczbę zmienionych wierszy i stan bazy. Dodaj test obcego conversation_id oraz listy źródeł przed modelem.
```

## Odbiór

Dozwolone operacje nadal działają; obce SELECT nie ujawnia wierszy; fałszywy owner nie zapisuje; cudze UPDATE/DELETE nie zmieniają danych; RPC respektuje właściciela; model nie dostał obcego znacznika. NOT RUN jest lepsze niż fikcyjny PASS.

**Ratunek:** napraw jedną tabelę i sprawdź ją ponownie, nie wyłączaj RLS globalnie. **STRETCH:** osobna przestrzeń zespołu z tabelą membership; user_id sam w sobie nie modeluje członkostwa organizacji.
