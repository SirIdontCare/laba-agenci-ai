# L04 · W3 — Zepsuj narzędzie, nie całe zajęcia

**CORE: 20 min. Efekt:** działający scenariusz awarii i bezpieczny restart. Wymagane: W1/W2.

## Zrób

1. Dodaj tryb testowy adaptera: poprawny wynik, timeout, 429, nieprawidłowy JSON. Nie przeciążaj prawdziwego dostawcy, aby wymusić 429.
2. Dla odczytu dopuszczaj najwyżej jedno ponowienie na przejściowy błąd w ramach budżetu runa; uwzględnij Retry-After. 401/402 i błędy kontraktu nie uruchamiają ślepej serii ponowień.
3. Fallback to nowy model zaakceptowany przez Laba o tych samych wymaganych możliwościach. Zapisz actual_model. Nie ignoruj wymagań tools/JSON, aby uzyskać jakąkolwiek odpowiedź.
4. Przerwij run przyciskiem STOP. Pokaż częściowe wyniki i powód. Odróżnij zatrzymanie oczekiwania w UI od faktycznego anulowania pracy po stronie serwera.
5. Widok /runs pokazuje sukces, partial i failed. Zapisz prompt_version, źródło błędu i użycie wszystkich kroków. Nie loguj Authorization ani pełnych prywatnych payloadów.

## Polecenie do asystenta

```text
Dodaj kontrolowane awarie do adapterów i testy pętli. Retry tylko dla odczytu i przejściowych błędów, z globalnym limitem i timeoutem. Fallback nie może zmieniać uprawnień ani naruszać allowlisty. Przerwanie i częściowy wynik muszą być widoczne. Nie ukrywaj błędów pod ogólnym success:true.
```

## Odbiór

Timeout kończy się w limicie; 401 nie jest ponawiane; fallback jest widoczny; brak zgodnego modelu kończy run; STOP blokuje następne tool call; metryki obejmują koszt błędu. Testy offline nie naliczają kosztu modelu.

**Ratunek:** uruchom tylko jeden tool z kontrolowaną awarią. **STRETCH:** porównaj jeden mocniejszy model z kilkoma krokami słabszego na tej samej misji — liczy się koszt poprawnego wyniku.

**Praca domowa L04:** własna misja wielokrokowa, jeden sukces, jedna awaria i jedno zatrzymanie. Zapisz log oraz checkpoint L04.
