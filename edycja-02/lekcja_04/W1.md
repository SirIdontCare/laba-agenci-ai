# L04 · W1 — Pętla, która naprawdę potrafi się zatrzymać

**CORE: 15 min. Efekt:** kontrolowany run z osią zdarzeń. Wymagane: narzędzia L03.

## Zbuduj

1. Zamiast jednego „magicznego promptu” uruchom pętlę: model proponuje → backend waliduje → tool wykonuje → wynik wraca → model wybiera następny krok. Zachowuj identyfikatory tool calls. Nie usuwaj wymaganych przez provider niejawnych danych protokołu, ale nie pokazuj ich jako pełnego myślenia.
2. Ustal niezależne limity: 6 kroków modelu, 8 wykonanych tools i 45 sekund na run. To startowe wartości dydaktyczne. Jeden krok modelu może zaproponować kilka tools; nie utożsamiaj tych liczników.
3. STOP ma powód: completed, missing_data, approval_required, step_limit, tool_limit, timeout, cancelled lub error. Przekroczenie limitu to partial/failed, nie pełny sukces.
4. UI pokazuje rzeczywiste zdarzenia: rozpoczęcie, żądanie narzędzia, wynik/błąd i koniec. Plan tekstowy to deklaracja, wynik narzędzia to dowód.
5. Przed każdym nowym działaniem sprawdzaj uprawnienie, pozostały budżet i limit. Nie ufaj instrukcji modelu „jeszcze jeden krok”.

## Polecenie do asystenta

```text
Dodaj ograniczoną pętlę tools zgodną z zainstalowaną wersją SDK albo adapterem HTTP. Przeczytaj lockfile, nie kopiuj maxSteps ze starego kursu. Licz kroki modelu, tools i czas oddzielnie. Każda ścieżka ma stop_reason. Dodaj kontrolowany adapter testowy, który zawsze prosi o kolejne narzędzie, i udowodnij zatrzymanie bez płatnych wywołań.
```

## Odbiór

Zwykła odpowiedź kończy run; powtarzające się tool calls kończą się limitem; nieznany tool nie jest wykonywany; anulowanie nie rozpoczyna następnego kroku. Raport usage obejmuje wcześniejsze kroki. Twardy timeout obejmuje także sieć narzędzia.

**Ratunek:** najpierw dwa kroki z adapterem offline; dopiero potem model live. **STRETCH:** wykrywanie powtarzanego odczytu o identycznych argumentach i jawna odpowiedź z cache. Nie cache'uj cudzych danych pod wspólnym kluczem.
